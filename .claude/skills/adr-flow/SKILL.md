# 决策 → 实现 → 评审

这个仓库的历史就是它的文档：`docs/adr/` 是决策，`--selftest` 是缺陷清单，提交信息是
推理过程。这个流程存在，是为了让新改动继续是这样，而不是退化成"改完能跑"。

常驻不变量（构建门槛、分支规则、常踩的坑、仪器清单）在 `CLAUDE.md`，这里只讲流程。

## 先过入口闸门

两问，按顺序：

**① 有没有一个具体的、观察到的东西逼出这个改动？**

一个看到过的缺陷、一次测量、或一条被证实的机制事实。这是仓库里几乎每篇 ADR 的第一句：

> *A card titled `swift` kept appearing for about a second and vanishing.*
> *Seven defects landed in one small region of this codebase.*
> *Scanning every two seconds around the clock cost about 34 minutes of CPU a day.*
> *An amber card appeared on the dashboard while the ambient band stayed dark.*

**② 如果这是一个押在价值上的赌（"这样会不会更好"），能不能说出什么会证伪它？**

只有这类决策需要第二问。ADR-0014、0015、0022 是 22 篇里仅有的三篇写了证伪方式的，也
正是仅有的三篇在赌价值。机制/正确性类的不需要：把 `argv[0]` 和整条命令行分开不需要
证伪方式，它需要的是那张幽灵卡片。

**①答得上 → A（写 ADR）。①答不上 → B（先 grill）。**

①答不上意味着你手上是偏好或直觉。②答不上而①答得上，说明你在改一个已知的坏掉的东西，
直接走 A。

琐碎改动不走这个流程。判据：它会不会让某条 ADR 变成假的？会 → 走流程。

## A. 想清楚了：从 ADR 开始

### A1. 读相关 ADR —— 但**不要直接相信它**

这是这个仓库最贵的一课。它对"代码不符合 ADR"很敏感（`--selftest` 每条断言都是），
但对"ADR 不符合代码"**没有任何检查手段**。一次全面对照查出 8 处不一致，**一半是 ADR
错了**：四处描述的机制从未实现过（ADR-0008 的 FSEventStream、ADR-0013 的每屏偏移、
ADR-0010 的按老化删文件、ADR-0005 的 end 事件即移除），四处落后于代码。

所以：ADR 提到的每个符号、常量、机制，**先确认它今天还在**。

```bash
grep -rn "<ADR 里点名的符号>" swift/Sources/
```

### A2. 对不上时，先判定方向，再决定改哪边

三种结论，修法完全不同：

| 结论 | 判定方式 | 修法 |
|---|---|---|
| ADR 落后于代码 | 改动的提交没碰 ADR | 改 ADR |
| ADR 写了从未实现的东西 | `git log -S` 全空 | 补实现，或标 deferred |
| 代码回归了 | `git log -S` 有加、有删 | 改代码 |

```bash
git log --oneline -S'<精确字符串>' -- <path>   # 这行何时加、何时删
git show <rev>:<path>                          # 那一刻树里的真实内容，不是 diff 片段
git show <rev> --stat                          # 那次提交碰了哪些文件（碰没碰 ADR）
```

**看树内容，不要只看 diff 片段。** 一次回归的定性就是这么翻出来的：`0d06661` 引入
`sessions[index].pid = hook.pid`，`bb2b7b5` 主动加强它并在**同一次提交**写下依赖它的
ADR 句子，`df8b82d` 重构时把 `isRunning` 校验搬走、赋值跟着一起删了。丢了两天，提交
信息里一个 `pid` 字都没有——有意取舍会改注释。

### A3. 写 ADR

标题是一句主张，不是任务名（"Waiting is only ever reported"，不是"改进等待状态"）。
必须包含：

- **决策**，以及**被否掉的方案为什么不行**
- **代价**——每条 ADR 都点名自己换掉了什么
- **怎么证伪**：一个具体的观测 + 现成的仪器（`tools/dead-wait.py`、`tools/band-probe.swift`、
  `--selftest`）
- **证据来源标注**：抓到现场了，还是只是症状吻合？没抓到就写"诚实标注：这次没抓到
  现场，判据是……"，并留下判据

改老 ADR 用 `> **……**` 引用块就地修正，不要重写历史。整体作废才加 `status:` 头。

**ADR 先落定，再动代码。** 两边对不上时先把 ADR 改对——否则后面的实现和评审是在拿一个
已知错误的基准做比对。

### A4. 实现

- 每个修好的缺陷留一条 `EvidenceChecks` 断言。测不了的就抽成纯函数再测——`applying(_:to:)`
  和 `retainedVisits(_:now:)` 都是这么来的
- 断言要钉住**结构**而不只是行为：`retainedVisits` 不接收会话列表，"按缺席清除"因此
  写不出来，而不只是没写
- 顺手发现的、超出本次范围的问题：说出来，让人决定什么时候做，不要顺手改掉

## B. 没想清楚：先 grill

调用 `eden-dev:grill-with-docs`——它会拿现有领域模型（CONTEXT.md + ADR）来质询你的想法，
并在决策成形时就地更新文档。

**不要跳过它自己写 ADR。** 一条没有观察逼出来的 ADR，是把偏好包装成决策，而 ADR 是
规范——它一旦写下，后面所有代码都要向它对齐。这个仓库为写错的 ADR 付过账：四篇描述了
从未实现的机制，而且因为没有任何检查手段，它们一直被后来的 ADR 当作前提引用。

**退出条件**：闸门的①能答上了——你手上有了一个具体的东西，而不是一个想法。然后进 A1。

---

## C. 代码完成：PR 与评审

分支和硬性门槛见 `CLAUDE.md`。

**一个提交一件事。** 文件重叠导致拆不开时，宁可合成一个提交并在信息里分节列清，也不要
伪造一个不曾发生的顺序。

**提交信息承载推理**（CLAUDE.md 说了这条，这里是完整形式）：

- 症状——看到了什么
- 机制——为什么会这样
- 考古——如果是回归：哪次提交引入、什么时候删的、活了多久
- 验证——怎么证实的
- 诚实标注——没验证到的部分，以及留下的判据

**评审是必经的，不是可选的：**

```bash
/code-review        # 提 PR 前，评审这个分支
gh pr create        # 远端是 GitHub: TsichiChang/CodeMonitor
/review             # PR 建好之后
```

`/code-review ultra` 是更重的多 agent 云端评审，**只能由你手动触发**，Claude 不能代劳。

评审要专门看两件事：新代码有没有让某条 ADR 变假；有没有制造第二处同义表达（见下）。

## 每个阶段都成立的规则

**1. 验证优先于断言。** 每个结论要么有证据，要么明确标注没有。构造 fixture 是最快的
路径——用 `CODEMONITOR_STATE_DIR` 指向临时目录写假的 hook state，`--diagnose` 就会读它。

**2. 测量，不要估算。** "光带耗多少 CPU" 拒绝估算、跑了 `band-probe`，量出 11.5% 一个
核——比 ADR-0008 判定必须换掉的轮询还贵一倍，而且从来没进过任何一次测量。估算会给出
"大概还行"，然后什么都不会发生。

**3. 两处表达同一件事必然漂移。** 这个仓库付过至少六次账：`dismissWidth`、
`inAttentionOrder`、`namesNoProject`、`headerHeight`、`counts`、`json_field`/`carry`。
发现第二处表达时**合并它，不要加条件**。能改成派生就派生——`counts` 改成计算属性之后，
那类缺陷不可能再出现。

**4. 不能被工具证实的，标注出来。** 不要把推测洗成发现。

**5. 被质疑时先重新推导，不要辩护。** ADR-0022 的判据从"应用级不可能"改成"标签页级"，
就是因为一次质疑是对的——我把"在同一个 app 里"和"看不见"混为一谈了。判定对方对的时候
说清楚，然后改**产物**，不只是改口。

**6. 验证手段本身也会骗人，而且骗法不止一种。** CLAUDE.md 记了两个常踩的（`--diagnose`
是另一个进程；截屏类 API 无声地要权限）。更一般的形式是：**一次测量只证明它测的那件
事**。光带改成 CALayer 之后 CPU 是 0%，但画反了也是 0%——方向必须另外验一次。做完一次
验证，问一句"如果我错了，这个数字会变吗"。

仪器清单在 `CLAUDE.md`。
